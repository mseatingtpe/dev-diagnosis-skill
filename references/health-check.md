# 健康檢查機制

目標：防止既有 skill 清單腐敗，確保診斷階段查到的資訊是正確的。

這不是分診的第五個階段，而是一個持續運作的背景機制，分兩層：

## 第一層：定期檢視

由負責人定期（建議每季）檢視既有 skill 清單。可以手動檢查，也可以請 AI 工具輔助掃描（例如用 Claude Code 檢查 repo 的最後 commit 日期）。

檢查重點：
- 清單中每筆紀錄的「最後確認日期」是否過期
- GitHub repo 是否還有在維護
- Skill 的使用狀況是否跟登記時一致

如果工作站後續建立了自動掃描腳本，可以替代手動檢查，但不是前提條件。

## 第二層：判斷處置

對每個過期或有疑慮的項目，判斷處置方式：

- **維持**：仍在使用，更新「最後確認日期」
- **更新**：需求變了，走 dev-diagnosis 的「現有工具的問題」入口重新診斷
- **下架**：已無用途，在 skill 清單中標記為「已棄用」，保留紀錄但不再出現在復盤結果中

## 健康檢查的工作站設定

每個工作站在設定檔中定義自己的檢查參數：

- 掃描頻率：（每週 / 每月 / 每季）
- 閾值天數：（超過幾天未更新標記為「待確認」）
- 通知管道：（Slack channel / email / 其他）
- 負責人：（誰收到報告、誰做最終判斷）

## 與診斷階段的銜接

階段一的「既有 skill 復盤」在查詢 skill 清單時，應自動過濾掉狀態為「已棄用」的項目，只顯示「使用中」和「待確認」的。遇到「待確認」的項目時，提醒使用者：「這個 skill 已經一段時間沒更新了，建議先確認它還能不能用。」
